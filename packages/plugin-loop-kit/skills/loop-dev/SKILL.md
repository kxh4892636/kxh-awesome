# 日常开发流程

`loop-dev` 是 plugin-loop-kit 的日常交付路由。它负责在想法到已验证交付之间选择最小可信路径，只编排已有 skill，不复述各 skill 的内部实现。

## 输入

选择路线前，先明确：

- 目标：用户期望什么结果，必须交付什么产物，哪些内容不在范围内。
- 事实与假设：哪些信息已从仓库、文档、命令输出、用户消息或浏览器验证，哪些仍未确认。
- 影响面：可能受影响的文件、模块、接口、用户路径、数据、命令、文档或外部系统。
- 验证方式：能证明改动生效且不破坏相关路径的最小可信证据。

如果某个问题能通过读取仓库回答，先读取仓库，不要直接问用户。

## 主流程：想法到交付

普通功能开发和边界清晰的代码改动使用这条路线。

1. **用 `grilling` 讨论**
   - 使用 `grilling` 澄清需求、约束、高风险假设和分支决策。
   - 每次只问一个阻塞问题。
   - 高确定性问题只有在本地上下文可验证后才自动确认，并明确告知用户。
   - 完成标准：目标行为、范围、验收信号和排除项都已明确。

2. **分支：是否需要文档**
   - 只有用户要求 PRD、需要产品口径对齐，或需求边界不稳定时，才使用 `to-prd`。
   - 用户要求前端技术文档，或需要说明 API、交互、数据、监控、模块工作时，使用 `to-tech`。
   - 任务涉及 Lark/飞书文档、Wiki、富文本编辑或画板/图表质量时，使用 `lark-doc-quality`。
   - 普通单会话开发跳过文档生成。
   - 完成标准：必要文档产物已生成，或该分支已明确跳过。

3. **分支：是否需要计划文档**
   - 小改动跳过 `to-plan`：目标清晰、影响面单一、可在当前上下文完成、验收路径明确。
   - 跨模块、多轮、多会话、验收复杂、存在交接风险、用户明确要求计划文档，或需要其他 agent 接续状态时，使用 `to-plan`。
   - 多会话工作优先用 `to-plan` 和 TaskList 维护状态，不强制先生成 PRD。PRD 是可选分支，不是必经步骤。
   - 如果使用 `to-plan`，计划完成后必须暂停，等待用户确认后再进入实现。
   - 完成标准：计划文档已保持最新，或该改动已被判定为足够小、可不创建计划文档。

4. **选择开发循环**
   - 前端页面、组件、交互、表单、路由、权限、空态/错误态和类 E2E 用户行为使用 `bdd`。
   - 后端逻辑、库、CLI、脚本、纯逻辑、API 行为和面向公开接口的集成式验证使用 `tdd`。
   - 只有低风险、非代码或必须实现后才能有效验证的代码任务，才使用瀑布式循环。
   - 完成标准：已命名所选循环和第一个垂直切片。

5. **执行垂直切片**
   - 一次推进一个切片：一个行为或场景、一个失败或可变红的检查、最小实现，然后验证。
   - 禁止先写完所有测试，再一次性完成所有实现。
   - 将 `code-spec` 作为底层代码规范入口，只读取本次实际触碰的语言、框架、API、Vite+、React Query、Zod、Ant Design 或 Go 分支。
   - 只有切片涉及浏览器自动化、截图、E2E 行为、页面调试、抓取或视觉验证时，才使用 `browser-use`。
   - 如果启用了 `to-plan`，TaskList 状态、关键决策、验证结果、commit 或阻塞变化后立即更新计划。
   - 所有垂直切片完成后，进行整体验收；
   - 完成标准：每个切片的行为已实现、检查完成，并以证据标记为通过或阻塞。

6. **用 `verify` 验证**
   - 代码改动、需要验收的文档更新、缺陷修复、前端流程、API 变更、构建/配置变更或发布前检查后，使用 `verify`。
   - 根据真实影响面选择最小可信验收矩阵。
   - 失败项只在范围内修复，并只重跑失败检查和直接受影响的相邻检查。
   - 完成标准：最终回复能说明通过/失败/待确认、证据和残余风险。

## 独立入口

### 缺陷或性能问题

当用户报告 broken、failing、slow、flaky、throwing，或要求 debug、diagnose 时：

1. 先使用 `diagnosing-bugs`，不要进入普通功能路线。
2. 为用户描述的精确症状建立紧反馈循环，且该循环必须可变红。
3. 复现、最小化、排序假设、一次只探测一个变量，然后修复。
4. 只要存在正确测试缝隙，就补回归测试。
5. 运行 `verify`。
6. 如果真实发现是缺少良好测试缝隙，在修复后或阻塞记录后建议进入 `improve-codebase-architecture`。

### 架构改进

当用户要求架构改进、重构机会、模块深化、提升可测试性或提升 AI 可导航性时：

1. 先使用 `improve-codebase-architecture`。
2. 先产出架构候选报告，不要直接进入实现。
3. 用户选定候选后，使用 `grilling` 对齐设计。
4. 实现阶段回到主流程：需要时 `to-plan`，否则按小改动直做，然后 BDD/TDD 和 `verify`。
5. 普通开发中，只有在红/绿切片或诊断后暴露真实结构问题时才调用该路径，不提前扩大范围。

### 浏览器工作

`browser-use` 是工具路由，不是固定阶段。

以下场景使用：

- 前端 BDD 或类 E2E 验证。
- 页面检查、点击、输入、截图对比、抓取或视觉检查。
- 仅浏览器环境可复现行为的运行时调试。

后端、库、CLI、纯计划或纯文档任务不使用它，除非浏览器本身就是被测系统。

## 分支规则

- `to-prd` 是可选分支。多会话或多 issue 工作不强制使用它。
- `to-plan` 是条件分支。小改动跳过它。
- `bdd` 和 `tdd` 是垂直切片循环，不是批量写测试阶段。
- `code-spec` 是底层参考。只读取与本次代码改动相关的分支。
- 除非用户明确要求不验证，否则所有代码改动或带验收含义的改动都由 `verify` 闭环。
- `loop-boot` 和 `loop-kit-update` 不纳入本交付流程。

## 完成汇报

完成后只汇报：

- 采用的路线及原因。
- 修改的文件或生成的产物。
- 已运行的测试或验证，以及通过/失败/待确认结果。
- 跳过的分支及原因。
- 残余风险或阻塞项。
