# Verify

本 skill 是交付验收路由。目标不是把所有检查都跑一遍，而是围绕用户目标、改动影响面和失败代价，选择最小但足够可信的验证闭环。

## 完成标准

一次验收完成时，应能回答：

1. 本次改动影响哪些组件、接口、命令、数据、配置、环境或用户路径。
2. 项目声明的相关检查是什么，实际选择了哪些检查，为什么这些检查足够覆盖本次风险。
3. 静态检查、测试、构建、运行时验证、接口验证、数据验证、迁移验证或人工验收是否通过。
4. 失败项是否已定位、修复，并完成最小范围重验；已通过项无需重复验收，除非修复影响它。
5. 缺少权限、依赖、数据、环境或外部服务时，是否明确标为待确认/阻塞，并说明缺口。
6. 验收结论是否包含通过/失败/待确认、证据、残余风险和下一步。

## 边界原则

- 不默认使用任何特定工具名、包管理器、构建命令、浏览器插件、日志平台、发布环境或流水线。
- 当项目或用户提供专属验收 skill、运行手册、发布文档、环境说明或业务流程时，先读取对应材料，再把它作为本次验收矩阵的补充。
- 缺少项目事实时，不猜测命令。优先读取最近的 `AGENTS.md`、README、package/build/test 配置、Makefile、CI 配置、脚本目录或用户提供的验收说明。
- 验收阶段默认只执行验证命令。自动修复、格式化写入、迁移、发布、清理数据、重启服务等有副作用操作，必须有项目约定或用户授权。

## 总流程

按顺序执行，除非用户明确要求跳过某一类验证：

1. **定义验收目标**：确认用户要证明什么，例如“修复是否生效”“改动是否可发布”“接口契约是否兼容”“页面路径是否可用”“脚本输出是否正确”。
2. **识别影响范围**：根据变更文件、调用链、配置、数据模型、入口点和项目文档，列出受影响对象与不受影响范围。
3. **建立验收矩阵**：按风险选择验证项。常见维度包括静态检查、单元测试、集成测试、端到端测试、构建/打包、运行时冒烟、API/契约验证、数据库/迁移验证、兼容性验证、安全/权限验证、性能基线和人工确认。
4. **执行最小可信验证**：优先运行项目声明的最窄命令或最小用户路径。没有现成命令时，构造可重复的轻量验证方式，例如 CLI fixture、curl/HTTP 请求、测试脚本、浏览器脚本、一次性检查清单或数据查询。
5. **定位并修复失败项**：失败后先判断是代码问题、测试/脚本问题、环境问题、数据问题、权限问题还是外部依赖问题；只修复授权范围内的问题。
6. **最小范围重验**：修复后只重验失败项及受修复影响的相邻项。不要因为单个失败点重复跑所有已通过检查。
7. **报告结论**：结论前置，列出验收范围、执行项、证据、失败/阻塞、残余风险和建议。

## 验收矩阵选择

根据改动类型组合使用以下验证方式：

| 改动类型               | 优先验证                                                                  |
| ---------------------- | ------------------------------------------------------------------------- |
| 纯文档、配置说明、注释 | 格式/链接/示例命令审阅，必要时运行文档示例                                |
| 库函数、算法、纯逻辑   | 单元测试、fixture、属性/边界用例、类型检查                                |
| CLI、脚本、批处理任务  | fixture 输入输出、退出码、错误路径、幂等性和文件副作用检查                |
| 后端接口、服务逻辑     | 单元/集成测试、HTTP/gRPC 请求、契约校验、鉴权/错误路径、数据读写验证      |
| 数据库 schema 或迁移   | 迁移 dry run、回滚策略、读写兼容性、种子数据或快照验证                    |
| 前端 UI 或交互         | 组件测试、浏览器用户路径、无障碍/响应式关键断言、网络请求与页面状态一致性 |
| 构建、打包、发布配置   | 目标包/服务的构建或打包、产物存在性、入口可启动、配置加载验证             |
| 跨模块或混合改动       | 从最外层用户路径或服务调用路径验证，再补充关键单元/契约检查               |

## 接口与运行时验证原则

接口验证和运行时验证应沿真实调用路径进行：

1. 检查传入参数、状态码/错误码、响应结构、核心字段、边界输入和权限场景。
2. 对 UI 或客户端消费接口的场景，同时确认接口返回和消费结果一致。
3. 对服务间调用，确认请求契约、序列化格式、超时/重试、错误映射和兼容性。
4. 对数据写入，确认持久化结果、事务边界、重复执行行为和回滚/补偿策略。
5. 出现错误时，收集项目通用证据：错误消息、请求 ID/trace ID、日志片段、命令输出、截图、响应样例或最小复现。不要假设某个组织专用日志字段或排障平台存在。

## 验收循环

验收是“检查 → 修复 → 最小重验”的循环，直到全部通过或出现明确阻塞。每轮都记录失败点、修复动作和重验结果。

1. **检查命令失败**：先确认命令、依赖、环境变量和工作目录是否符合项目文档；如果是代码问题，修复后只重跑失败命令或更窄命令。
2. **测试失败**：确认失败是否覆盖本次目标。若是相关失败，修复后重跑该测试及直接依赖的测试；若是不相关历史失败，记录为残余风险并说明证据。
3. **运行时失败**：保留最小复现步骤、输入、环境和输出。修复后重放同一复现，再补一条相邻成功路径。
4. **接口或契约失败**：定位请求、响应、错误映射、数据消费或兼容性问题。修复后重验触发该接口的最小调用路径。
5. **数据或迁移失败**：先保护现场和可回退性。修复后验证迁移、读写、回滚或补偿路径。
6. **环境或外部依赖失败**：不要把不可控环境故障伪装成代码验收失败。记录依赖、缺口、已尝试动作和需要用户/平台/owner 处理的事项。
7. **停止条件**：所有失败项完成重验并通过；或缺少权限、数据、环境、依赖服务、仓库访问、发布能力等导致无法继续。

## 专属流程扩展

verify 不承载专属流程。以下内容应由项目文档或额外 skill 补充：

- 特定前端框架、构建工具、包管理器、浏览器插件或端侧调试工具。
- 特定后端语言、RPC 框架、日志平台、trace 系统、错误码体系或数据库工具。
- 特定公司/团队的发布环境、流水线、审批、灰度、回滚和监控平台。
- 特定业务域的账号、权限、数据准备、验收路径、合规要求和报告模板。

当用户明确要求某个专属流程，且对应 skill 可用时，先读取该 skill，再把它作为本次验收矩阵的一项；不要把它提升为所有项目的默认流程。
