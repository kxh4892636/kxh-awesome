# Loop Dev

你不需要记住 plugin-loop-kit 的每个 skill。`loop-dev` 是一个路由流程：把一个需求从想法推进到可验收交付，并在每个阶段选择正确的专项 skill。

本 skill 只做编排和路由。专项规则以对应 skill 为单一事实源，不在这里复制内部实现。

## The main flow: idea -> ship

大多数开发任务走这条主线：

1. **需求**：定义目标、交付产物、验收标准、不做范围。
2. **讨论**：使用 `grilling` 逐个问题对齐需求、约束、分支和风险。
3. **计划**：按影响面和依赖关系拆成纵向切片；复杂或多会话任务使用 `to-plan` 记录计划。
4. **测试**：先根据 `verify` 的验收矩阵设计可失败测试，再按任务类型进入 `bdd` 或 `tdd`。
5. **开发**：按 BDD/TDD 的 Red -> Green -> Refactor 纵向循环实现。
6. **验收**：使用 `verify` 建立验收矩阵，同时回查 `bdd`/`tdd` 场景、测试证据和未覆盖风险。
7. **交付**：报告结论、验证证据、残余风险和后续动作。

默认选择 TDD/BDD，不走瀑布。前端页面、组件、交互、表单、路由、接口消费、权限态、空态和错误态走 `bdd`；后端、库、纯逻辑、CLI、数据处理和算法走 `tdd`。

## Branches

### 需求不清

使用 `grilling`。

- 一次只问一个问题。
- 如果问题能通过读取仓库回答，先读仓库，不把问题抛给用户。
- 必须对齐目标、范围、验收标准、约束、风险和优先级。
- 讨论结束条件：需求足够生成测试/验收路径，且不依赖未确认的关键假设。

### 需要沉淀文档

按产物选择：

- PRD：使用 `to-prd`，从当前对话和已验证代码事实综合，不重新采访用户。
- 前端技术文档：使用 `to-tech`，说明数据源、功能模块、交互逻辑、数据逻辑和 TODO。
- 飞书文档、Wiki、Docx、会议纪要、技术方案、产品方案、画板或富文本排版：使用 `lark-doc-quality`。

文档分支结束后，若文档产生开发任务，回到主流程的计划阶段。

### 需要长期或多会话执行

使用 `to-plan`。

- 将计划写入 `docs/plan/{sessionID}.md`。
- 计划必须包含环境变量、TaskList、引用资源和推荐技能。
- TaskList 按纵向切片拆分，每个切片都要有对应测试或验收路径。
- 目标、范围、验证结果、风险、阻塞、commit、PR 或上下文变化时，增量更新计划。

### 开发实现

先用 `code-spec` 路由代码规范，再按类型进入测试驱动循环。

- 前端行为：使用 `bdd`。先写 Given / When / Then 场景，确定测试层级，再写实现。
- 后端、库、纯逻辑：使用 `tdd`。通过公共接口写一个可失败测试，再最小实现。
- Vite+、React、Vue、Go、接口请求、React Query、Zod、Ant Design 或依赖相关任务：按 `code-spec` 的任务路由读取最小必要 reference。

每个切片只推进一个行为：Scenario/Test -> Red -> Green -> Refactor -> Regress。不要先批量生成所有测试，再批量实现。

### 测试设计

测试用例必须从验收路径反推。

1. 先按 `verify` 识别影响范围和验收矩阵。
2. 将验收矩阵中的高风险项转成 BDD 场景或 TDD 行为测试。
3. 每个测试都要能回答它对应哪条验收风险：静态检查、单元测试、集成测试、端到端测试、构建、运行时冒烟、接口验证、数据验证、兼容性或人工确认。
4. 测试期望值必须来自需求、接口契约、固定样例、设计稿或业务规则，不能复用实现逻辑计算期望。
5. 如果无法建立可信测试，停止开发，说明缺少的信息、替代验证方式和剩余风险。

完成标准：测试清单和验收矩阵能互相追溯；没有孤立测试，也没有未解释的关键验收风险。

### 问题修复

难复现 bug、性能回归、报错、失败或慢路径先使用 `diagnosing-bugs`。

- 先建立 tight feedback loop：一个能捕获用户具体症状的可运行命令。
- 复现并最小化后，提出 3-5 个可证伪假设。
- 修复前尽量把最小复现转成回归测试。
- 修复后回到主流程验收阶段。

如果发现没有合适测试 seam，记录为架构风险，并在交付后建议进入 `improve-codebase-architecture`。

### 架构健康

重构、架构改进、模块加深、测试 seam 改善或 AI 可导航性优化，作为独立入口使用 `improve-codebase-architecture`。

- 先生成架构报告，不直接提出接口方案。
- 用户选中候选后，用 `grilling` 对齐约束。
- 如果候选变成具体开发任务，回到主流程的需求或计划阶段。

### 浏览器验证

涉及真实页面、交互、截图、E2E、网页抓取或本地应用验证时，按可用环境选择浏览器 skill。

- 需要直接 CDP 控制或站点交互时使用 `browser-use`。
- 前端 BDD 的浏览器路径仍以 `bdd` 的场景为验收语言，以 `verify` 的验收矩阵为覆盖标准。

## Acceptance

验收阶段同时参考 `verify` 和对应的 `bdd`/`tdd` 结果。

1. 使用 `verify` 明确验收目标、影响范围和验收矩阵。
2. 对前端任务，核对 BDD 场景是否覆盖核心用户路径、可观察结果和异常流。
3. 对后端、库或纯逻辑任务，核对 TDD 测试是否通过公共接口验证行为，而不是实现细节。
4. 核对 Red/Green 证据：至少说明关键测试是否先失败、修复后是否通过；如果无法先红，说明原因。
5. 执行最小可信验证：测试、构建、静态检查、浏览器路径、接口请求或文档回读。
6. 失败后只修复授权范围内的问题，并最小范围重验失败项及受影响邻近项。
7. 交付结论必须包含通过/失败/待确认、证据、未覆盖场景、残余风险和下一步。

验收完成标准：`verify` 的验收矩阵、`bdd`/`tdd` 的测试证据和最终结论一致；任何未覆盖项都被明确标为待确认或残余风险。

## Context Hygiene

需求、讨论和计划留在同一个上下文中完成，避免丢失用户约束。多会话任务必须先用 `to-plan` 固化上下文，再拆分执行。

如果任务接近上下文上限，先更新计划文档，再在新会话中继续。不要在需求未定、测试未定或验收失败定位过程中随意切换上下文。

## Delivery Report

完成后按任务实际情况简要报告：

- 交付了什么；
- 使用了哪些 skill 和为什么；
- BDD/TDD 场景或测试文件；
- 验收矩阵和实际执行的验证；
- 通过、失败或待确认结论；
- 残余风险。

不要复制大段文档或测试输出。用户能在仓库或目标文档中查看完整产物。
