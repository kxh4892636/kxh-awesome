# Loop Dev

你不需要记住每个开发 skill 的触发条件，先从这里进入。

`loop-dev` 是一个用户手动调用的 router skill，只负责编排流程和阶段门禁，不替代各 skill 的内部规则。执行到具体阶段时，必须读取并遵守对应 skill。

## The main flow: idea -> ship

大多数开发任务走这条主线：

```text
需求 -> 讨论 -> 计划 -> 测试 -> 开发 -> 验收
```

1. **需求**
   - 明确目标、交付物、验收标准和不做范围。
   - 区分已验证事实、未验证假设、客观约束和主观决策。
   - 如果问题来自 bug、报错、失败、性能回退或不稳定行为，先走「Bug on-ramp」，不要直接进入普通开发主线。

2. **讨论**
   - 使用 `grilling` 一次只问一个问题，直到需求、约束、分支和验收路径足够清楚。
   - 能从仓库读取答案的问题，先探索代码库，不把可验证事实丢给用户确认。
   - 讨论结束后判断是否需要文档分支；不需要时直接进入计划。

3. **计划**
   - 使用 `to-plan` 创建或更新 `docs/plan/{sessionName}.md`。
   - 计划必须包含目标、范围、TaskList、验证用例、引用资源、推荐技能、风险和阻塞项。
   - TaskList 按垂直切片拆分：一个验证用例对应一个 task，不做先写完所有测试再统一实现的水平切片。
   - **计划阶段结束后必须等待用户确认，禁止自动进入测试或开发。**

4. **测试**
   - 前端页面、组件、交互、表单、路由、接口消费、权限态、空态、错误态或 E2E 任务使用 `bdd`。
   - 后端、库、CLI、纯逻辑、脚本或接口行为使用 `tdd`。
   - 先建立可执行或准可执行的行为测试，让它能在目标行为缺失时变红。
   - 如果无法建立可信测试，停止实现并说明缺少的信息、风险和替代验证方式。

5. **开发**
   - 使用 `code-spec` 作为底层工程规范；按任务类型读取最小相关 reference。
   - 一次推进一个垂直切片：Red -> Green -> Refactor，再进入下一个切片。
   - 只修改当前目标需要的文件，复用项目已有模式和工具链。
   - Refactor 只在 Green 后进行；如果发现 shallow module、测试 seam 差或耦合泄漏，记录为后续架构入口候选，不默认展开架构审查。

6. **验收**
   - 使用 `verify` 建立最小但可信的验收矩阵。
   - 前端代码验收必须纳入 `browser-use`：执行真实浏览器路径、截图、DOM/网络/交互验证或 E2E 冒烟，证明用户可观察行为成立。
   - 非前端任务按影响面选择静态检查、单元/集成测试、构建、CLI fixture、接口请求、数据校验或运行时冒烟。
   - 验收失败时定位、修复并做最小范围重验；通过项不重复跑，除非修复影响它。

## Documentation branches

文档不是主流程的默认阶段，只在命中场景时分支，在「讨论」阶段后触发。

- **`to-prd`**：用户明确要求 PRD，或需要把当前上下文沉淀成产品需求文档给非开发角色对齐。
- **`to-tech`**：前端实现影响较大，接口、交互、数据逻辑、模块拆分或发布方案需要先形成技术文档。
- **`lark-doc-quality`**：任务涉及飞书文档、Wiki、Docx、技术方案、产品方案、会议纪要、画板、图表或同步到飞书。

## Bug on-ramp

当用户报告 bug、报错、测试失败、线上异常、性能回退、慢、偶现或不稳定行为时，先使用 `diagnosing-bugs`。

流程门禁：

1. 建立 tight feedback loop：一个已经运行过、能捕获用户具体症状的命令或脚本。
2. 复现并最小化；不能复现就说明已尝试内容和需要的日志、录屏、HAR、环境或权限。
3. 给出 3-5 个可证伪假设，再按预测做 instrumentation。
4. 在正确 seam 写回归测试，修复后重跑原始反馈循环。
5. 清理临时日志和原型；如果真正问题是没有好 seam，记录并建议进入架构入口。

Bug 修复完成后仍回到 `verify` 做交付验收。

## Architecture entry

`improve-codebase-architecture` 是独立入口，不是每次开发的默认阶段。

使用它的场景：

- 用户明确要求架构改善、重构机会、测试性提升或 AI 可导航性改善。
- bug 诊断或 TDD/BDD refactor 阶段发现没有好 seam、模块 shallow、接口泄漏、调用方耦合严重。
- 需要先产出候选报告，让用户选择要深入设计的方向。

该入口先生成 HTML 架构报告并询问用户选择哪个候选；不要在报告阶段直接提出接口方案。

## Context hygiene

- 需求、讨论、计划必须留在同一个上下文中完成，避免丢失用户约束。
- 计划确认后再进入测试和开发；如果上下文接近失真或任务需要多会话拆分，先更新 `to-plan`。
- 每个子任务都必须保留自己的目标、验证用例、执行状态和验收结论。
- 发生目标、范围、TaskList、验证结果、阻塞、commit、PR 或上下文交接变化时，及时更新计划文档。

## Skill routing

| 场景 | 使用 |
| --- | --- |
| 需求讨论、方案追问、分支确认 | `grilling` |
| 会话计划、TaskList、上下文同步 | `to-plan` |
| 前端行为测试先行 | `bdd` |
| 后端、库、CLI、脚本、纯逻辑测试先行 | `tdd` |
| 工程规范、前后端代码规则、API、React、Vite+、Zod、AntD | `code-spec` |
| 验证、验收、回归、联调、冒烟、发布前检查 | `verify` |
| 前端真实浏览器验收、网页交互、截图、DOM/网络验证 | `browser-use` |
| bug、调试、失败、慢、性能回退 | `diagnosing-bugs` |
| 架构改善、深模块、测试 seam、AI 可导航性 | `improve-codebase-architecture` |
| PRD 产出 | `to-prd` |
| 前端技术文档 | `to-tech` |
| 飞书/文档/画板质量 | `lark-doc-quality` |

## Completion standard

一次 `loop-dev` 执行完成时，必须能回答：

1. 用户目标、交付物、验收标准和不做范围是什么。
2. 哪些事实已验证，哪些仍是假设或待确认。
3. 计划文档是否已创建或更新，且计划阶段是否经过用户确认。
4. TDD/BDD 的红绿闭环是否成立；如果没有，替代验证是什么。
5. 实现是否只覆盖当前目标，是否遵守 `code-spec` 和项目现有模式。
6. 验收矩阵覆盖了哪些影响面；前端代码是否完成 `browser-use` 真实浏览器验收。
7. 剩余风险、未覆盖场景、阻塞项和后续建议是什么。
