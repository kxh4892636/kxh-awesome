# BDD

本 skill 用于前端行为驱动开发。硬性前提：开发实现代码前，必须先确立 BDD 场景和对应测试路径；如果无法建立可信测试，先说明阻塞和替代验证方式，不要直接写业务实现。

## 核心原则

- 测试用户可观察行为，不测试实现细节。
- 用 Given / When / Then 描述业务场景，并把它映射为可执行或准可执行测试。
- 通过公开界面验证：页面文本、可访问角色、控件状态、URL、请求结果、可见反馈和业务状态。
- 一次推进一个纵向行为切片：一个场景、一个失败测试、最小实现、通过后再继续。
- 只在系统边界 mock：接口、时间、随机数、浏览器 API、路由入口和不可控外部服务。
- 不 mock 自己可控的组件、hooks、utils 或内部协作者来证明实现细节。
- 期望值必须来自需求、设计稿、接口契约、固定样例或业务规则，不要用与实现相同的逻辑重新计算期望值。

## 开发门禁

在写前端实现代码前，完成以下门禁：

1. 定义目标用户、入口页面、初始状态、用户动作和可观察结果。
2. 写出至少一个 Given / When / Then 场景，覆盖本次最核心行为。
3. 确定测试层级：
   - 用户跨页面或依赖真实路由、登录态、网络链路时，用 E2E / browser test。
   - 单页面复杂交互、表单、弹窗、列表状态时，用组件集成测试。
   - 纯函数、格式化、权限判断、query 解析时，可补充 TDD 单元测试。
4. 查找项目已有测试框架、测试目录、mock 方式和命令；沿用现有约定。
5. 先让 BDD 测试红起来，确认它能捕获目标行为缺失或错误。

如果第 2-5 步做不到，停止实现并向用户说明：缺少什么信息、为什么不能建立可信 BDD 测试、建议的最小补齐方案。

## 场景格式

BDD 测试应读起来像验收标准。下面是伪代码/风格示例，不是可直接复制运行的模板，实际执行 agent 会操作真实浏览器进行 E2E 验收，不需要写 E2E 测试代码；
优先使用简短、可执行的业务语言：

```gherkin
Scenario: 用户提交缺少必填项的表单
  Given 用户打开创建活动页面
  When 用户不填写活动名称并点击提交
  Then 页面展示“活动名称不能为空”
  And 表单不会发起创建请求
```

每个场景必须满足：

- Given 只描述用户可理解的前置状态，不描述 mock 细节。
- When 只描述用户动作或系统事件。
- Then 只描述可观察结果。
- 一个场景只证明一个核心行为；相关但独立的行为拆成下一个场景。
- 场景名描述业务能力或用户结果，不描述内部函数、组件层级或调用顺序。

## Mock 规则

只 mock 前端无法控制或不应真实调用的边界：

- 后端接口、支付/消息/上传等外部服务。
- 时间、随机数、浏览器存储、剪贴板、窗口尺寸、路由环境。
- 文件系统或平台能力。

不要 mock：

- 当前仓库内由本次实现控制的组件、hooks、utils、领域函数。
- 内部协作者的调用次数或调用顺序。
- 本应通过页面行为观察到的结果。

边界 API 应尽量是具体、稳定、类型明确的接口，例如 `getUser()`、`createOrder()`，而不是一个需要在测试里写大量条件分支的通用 fetch mock。

## 实施循环

对每个行为按以下循环推进：

1. **Scenario**：写 Given / When / Then，并确认它属于本次需求范围。
2. **Red**：写一个失败的 BDD 测试；失败原因必须对应目标行为缺失或错误。
3. **Green**：写最少实现代码让该测试通过，不提前实现下一个场景。
4. **Refactor**：在测试全绿后整理命名、组件边界、重复逻辑和可读性。
5. **Regress**：重跑当前测试和受影响的邻近测试；必要时补浏览器验收。

不要先写完所有测试再一次性实现所有代码。场景清单可以先建立，但测试和实现按纵向切片逐个闭环。

## Refactor 规则

只在 GREEN 后重构。重构候选包括：

- 重复逻辑。
- 过长组件、hook 或函数。
- 过浅模块：暴露太多细节、调用方需要知道太多内部步骤。
- 逻辑放错位置：数据和行为分离导致调用方拼装复杂。
- 原始值滥用：同一类业务概念反复用裸字符串、数字或对象拼接。
- 新代码暴露出的既有结构问题。

每次重构后重跑相关 BDD 测试，确保行为未变。

## 前端场景清单

按需求选择最小但可信的场景：

- 初始渲染：标题、关键数据、加载态、空态、权限态。
- 用户输入：表单填写、校验、联动、禁用态。
- 用户动作：点击、提交、取消、重试、删除、二次确认。
- 数据流：请求参数、成功态、失败态、刷新、分页、筛选、排序。
- 路由流：URL query、返回、跳转、新页面或弹窗。
- 异常流：接口失败、超时、无权限、脏数据、边界值。

优先覆盖失败代价高、用户路径核心、业务规则复杂、历史容易回归的行为。不要试图覆盖所有边界；先覆盖最能证明需求成立的行为。

## 交付要求

完成后输出：

- 已确立的 BDD 场景列表。
- 新增或修改的测试文件和测试命令。
- Red/Green 结果；如果无法先红，说明原因。
- 实现改动范围。
- 已执行的验证命令和结果。
- 未覆盖场景与剩余风险。
