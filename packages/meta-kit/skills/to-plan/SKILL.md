# To Plan

## 执行时机

- 用户手动要求创建或更新计划文档时，使用本 skill。
- compact/resume 注入上下文要求“immediately use the to-plan skill”时，立刻使用本 skill。
- 本 skill 必须维护 TaskList；任一 TaskList 任务完成、阻塞或状态变化后，必须立即更新计划文档。

## 工作流程

1. 确定当前项目根目录、sessionID 和计划文档绝对路径；如果当前目录在 Git 仓库内，以 Git 根目录作为项目根目录。
2. 如果计划文档已存在，先读取现有内容，再更新；禁止盲目覆盖仍然有效信息，执行增量更新操作，只删除确定失效信息。
3. 梳理最新用户意图、已验证事实、假设、决策、状态、TaskList、验证结果、风险和下一步。
4. 事实和假设必须分开写。无法验证但影响执行的内容，使用 `未确认` 标记。
5. 更新或创建 `docs/plan/{sessionID}.md`。新建文档或补齐缺失结构时，先读取 `references/plan-document-template.md` 并按模板生成；目录不存在时先创建目录。
6. 后续每完成任一 TaskList 任务，都把计划文档更新作为该任务完成前的最后一步，更新包含对应任务改动涉及的所有内容。

## 反模式：水平切片

**不要先写完所有验证方式，再一次性完成所有 task。** 这就是“水平切片”：把 RED 当成“列出所有验证方式”，把 GREEN 当成“完成所有 task”。

这会产生**低质量验证方式**：

- 批量写出的验证方式容易验证想象中的行为，而不是实际行为。
- 最终验证的是结构形状（数据结构、字段、接口形态），而不是用户可感知的结果。
- 验证方式会对真实变化不敏感：行为坏了也可能通过，行为正常也可能失败。
- 在真正理解 task 之前就过早承诺验证结构，后续容易返工。

**正确做法**：用垂直切片推进。一个验证方式 → 一个 task → 重复。每个验证方式都回应上一个循环学到的事实；因为刚完成对应 task，最清楚哪些行为重要、该如何验证。

```
错误（水平）：
  RED:   验证方式1, 验证方式2, 验证方式3, 验证方式4, 验证方式5
  GREEN: task1, task2, task3, task4, task5

正确（垂直）：
  RED→GREEN: 验证方式1→task1
  RED→GREEN: 验证方式2→task2
  RED→GREEN: 验证方式3→task3
  ...
```

## 如何验证

每个 TaskList 任务都必须先确认“如何知道它真的完成了”。验证方式不是装饰性字段，也不是事后补一句“已检查”；它是该 task 的完成标准。参考 TDD 的思路：先定义能失败的验证，再实现最小可交付变化，最后用验证结果更新计划。

确认每个 task 的验证方式时，按以下顺序思考：

1. 先把 task 改写成可观察结果：不要验证“做了某个动作”，要验证动作产生的结果。例如验证“计划文档包含最新阻塞原因和下一步”，而不是验证“更新了计划文档”。
2. 优先验证用户或接手模型能感知的行为：代码任务优先用测试、构建、类型检查、lint、CLI 输出、页面行为或 API 响应；文档和计划任务优先用目标文件内容、模板结构、状态一致性和关键事实覆盖情况。避免只验证内部实现细节、变量名、文件形状或字段存在。
3. 让期望值来自独立事实来源：期望结果应来自用户明确要求、已读取文件、命令输出、模板、规范或刚完成 task 的真实产物。不要用“我刚写进去的内容”反过来证明 task 正确。
4. 选择最强且贴近影响面的验证方式：能运行自动化测试就不要只静态阅读；能做聚焦命令就不要跑无关全量检查；内容任务可以用人工核对，但必须写清核对对象和通过条件。
5. 写清验证动作和通过条件：TaskList 中的验证方式要包含具体命令、文件路径、检查点或人工核对标准，以及预期结果。模糊说法如“检查无误”“确认完成”“简单验证”不够。
6. 无法验证时必须说明原因和替代证据：如果受外部系统、权限、时间或环境限制不能完成理想验证，写 `未验证`、原因、风险和最接近的替代验证；不要把未执行验证写成已通过。
7. 完成 task 前回填真实验证结果：task 进入 `completed` 前，必须把验证命令或核对结果记录到 `验证情况`。如果验证失败，task 不能标为 `completed`，应修正、降级为 `blocked`，或把新的修复 task 拆出来。

验证方式应当能回答三个问题：

- 验证什么结果：这个 task 对用户目标产生了什么可观察变化？
- 用什么证据验证：命令输出、测试结果、文件内容、渲染结果、用户确认还是外部系统响应？
- 什么算通过：预期输出、状态、字段、行为或内容覆盖标准是什么？

示例：

| task | 低质量验证方式 | 更好的验证方式 |
| --- | --- | --- |
| 更新计划文档 TaskList | 检查已更新 | 读取 `docs/plan/{sessionID}.md`，确认每个 task 都有状态、验证方式、当前验证结果，且与最新用户意图一致 |
| 修复 CLI 参数解析 | 看代码没问题 | 运行覆盖该参数组合的测试或最小 CLI 命令，确认输出和退出码符合需求 |
| 整理会议纪要 | 人工检查 | 对照原始纪要，确认决策、待办、负责人、日期和未确认项均被保留且没有把假设写成事实 |
| 修改前端交互 | 页面能打开 | 用浏览器或测试验证目标交互路径，确认用户可见状态变化正确且没有核心布局异常 |

## 自动更新触发点

下列变化都需要更新计划文档，因为接手模型需要看到最新事实，而不是只看到过期计划：

- TaskList 任一任务进入 `in_progress`、`completed` 或 `blocked`，或从阻塞恢复。
- 用户追加、收窄或改变目标、完成标准、不做范围或优先级。
- 新增、修改、删除关键文件，或完成一组可交付改动。
- 执行验证命令并得到通过、失败、跳过或未验证结论。
- 产生 git stage、commit、push、PR，或确认暂存区/工作区范围。
- 发现新的风险、阻塞、未确认项、环境限制或外部依赖。
- compact/resume 后上下文从计划文档恢复，且当前实际状态与文档不一致。

## 字段更新规则

- `目标`：用户改变目标、完成标准或不做范围时更新；不要把旧目标和新目标混在一起。
- `最新用户意图`：记录用户最近明确要求，尤其是会改变执行路径的补充指令。
- `当前上下文`：记录工作目录、相关文件、当前分支、运行环境和时间信息；文件路径使用绝对路径。
- `已确认事实`：只写已经通过文件读取、命令输出、用户明确说明或工具结果验证过的信息。
- `假设与未确认项`：写无法验证但会影响执行的内容，并用 `未确认` 标记。
- `已做决策`：写决策、原因和影响范围，避免接手模型重复推翻已经确认的路径。
- `当前状态`：同步已完成、正在进行、尚未开始和被阻塞的事项。
- `TaskList`：每个任务必须带状态和验证方式；验证方式必须说明验证对象、证据来源和通过条件；状态只使用 `pending`、`in_progress`、`completed`、`blocked`。
- `验证情况`：明确哪些验证通过、失败、跳过或未执行；未验证必须写原因。
- `关键改动/执行命令`：记录关键文件、命令和结果摘要；只保留能帮助继续执行的信息。
- `风险与注意事项`：记录最容易导致返工、误删、误提交、环境失败或理解偏差的点。
- `下一步`：按接手模型可以直接执行的顺序写，避免笼统描述。

## 内容约束

- 计划文档的完成标准是：接手模型不读取聊天记录，也能知道目标、事实、当前状态、风险和下一步。
- 必须保证内容的时效性，与最新上下文一致；不要只更新 TaskList 状态而遗漏验证方式或验证结果。
- 保留仍有效的旧信息，删除或改写已经失效的信息；不要盲目整篇覆盖。
- 不把推理过程大段塞进文档，只保留能指导继续执行的结论、证据和决策。
- 不把未验证猜测写成事实。
- 不记录敏感原文、凭据、密钥、账号或不必要的个人信息。

## 计划文档模板

- `references/plan-document-template.md`：计划文档完整模板，包含各标题下应填写内容的简要说明。
- 仅在创建新计划文档、修复缺失结构，或需要确认完整标题和 TaskList 表格格式时读取模板文件。
- 如果计划文档已存在且结构完整，优先基于现有文档和下方字段规则做增量更新，不需要读取模板。
